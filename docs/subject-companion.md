# Finite subject programs over an owned game

The portable and agent-kit distributions include `tools/subject_companion.py`.
It connects a separately pinned subject program to an already owned interactive
session. It does not launch Skyrim, prepare the world or acquire another game
owner. The ordinary executor establishes gameplay readiness first.

Use this route when a subject needs to retain a newly created NPC's exact
reference across subsequent checks. The origin supplies a finite Python
`run(exchange, emit)` function and its data-only plan. Review that trusted source
before execution: a hash identifies code, but does not make unknown code safe.
Keep frozen programs, plans, credentials and evidence outside Git. The transport
has no subject-name branches, numerical morph formulas or mod acceptance rules.

`exchange(envelope)` submits one existing machine action and returns its unchanged
raw result after exact delivery/completion verification. The transport verifies
the expected order, worker, game, session binding, completed common bootstrap,
frozen executor inventory and remaining deadline. It retains intent before the
single ingress attempt, verifies referenced result files and never replays an
uncertain action or reconnects to an old game session.

`emit(record)` durably retains the origin's records. The protocol includes:

- `check-start`: exact `caseId` and `role:"subject"`;
- `measurement`: case, sequence, request and intent/completed/unavailable delivery;
- `assertion`: case, check, actual/expected values and passed/mismatch outcome;
- `check-result`: case and passed/mismatch/unavailable/not_run outcome.

The first real matching native action delivery in the first declared case is
factual subject start. A readiness check, emitted start or ingress acknowledgment
alone cannot establish it. Native admissions and completed commands do not become
passed subject checks; the pinned origin program owns the actual assertions.
All raw records remain available beside the normalized report.

The transport executes the program in its own bounded child. On its deadline it
can stop only that retained child; game lifetime, input release and restoration
remain with the original executor/guardian. A subject mismatch can produce a
completed program with failed checks and normal game cleanup. Lost delivery or
unknown completion remains a technical fault. Game exit, subject outcome,
restoration and report delivery are independent facts.

For command arguments, run:

```powershell
python C:/Tools/skyrim-autotest/tools/subject_companion.py --help
```

Supply the operator's exact frozen executor inventory, expected native identities,
plan/program hashes, channel and current attempt. Do not guess these values or
use the command as another startup path. The standalone script ships with the
complete portable/agent-kit; a wheel installation alone is not that full source
distribution.

With Polygon, the separate Dashboard owns `polygon-file-plan/1` order validation,
explicit companion binding/admission, native lifetime and independently verified
case projection. Read its `docs/subject-companion.md`. A baseline proves only its
measured core lifecycle; new subject-specific binding declarations remain under
test. An expanded policy must never be relabeled as an old qualification.

Final results require an ended attempt, verified restoration, finished collection
and the exact report. Private runtime artifacts must not be attached to a public
release merely because the reusable client source is public. Audio remains a
separate connection and is not opened by this component.
